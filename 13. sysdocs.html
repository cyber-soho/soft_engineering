Lecture: System Documentation

Synthesized from Software Engineering Course - Chapter 8 (Requirements Modeling) & Chapter 21 (Software Testing)

1. Introduction: Requirements as Documentation

In Software Engineering, Requirements Modeling serves as the primary form of "System Documentation" during the early phases. As stated in Chapter 8, the written word is often insufficient for complex software. Technical work begins with a series of modeling tasks that lead to a specification.

The Requirements Model functions as the "blueprints" for the system. It uses a combination of text and diagrams to depict requirements in a way that is easy to understand and review for correctness.

2. Scenario-Based Modeling (Use Cases)

Use Cases capture the interactions between Actors and the System. They are vital documentation for defining how the system behaves from a user's perspective.

  • Actor: A role played by a person or device (e.g., Homeowner, Camera).
  • Use Case: A specific narrative of a usage scenario.

This modeling documents the static structure of the system. It defines the objects (Classes) that the system manipulates, including their Attributes (data) and Operations (behaviors).

4. Documentation Testing (Chapter 21)

Documentation is often neglected, but errors in documentation can be as catastrophic as errors in code. According to Chapter 21, Documentation Testing ensures that user manuals, help files, and installation guides are:

  1. Technically Accurate: Describing exactly what the system does.
  2. Usable: Written clearly (Editorial Review) for the target audience.
  3. Complete: Covering all functions and features.

Agile Manifesto - Note the contrast: "Working software over comprehensive documentation" does not mean NO documentation.

Tips

Tip for Exercise 1

Remember that a "Sensor" can be an Actor if it initiates interaction with the system. The "System" is the boundary. Actions should be specific: "System sends notification," not just "System works."

Tip for Exercise 2

Think about what data identifies a user. Do they have an access level (admin vs. guest)? What actions can they perform that the hardware cannot?

Tip for Exercise 3

Editorial = Style, Grammar, Clarity. Technical = Accuracy, Functionality. A sentence can be grammatically perfect but technically false.

Explanations

Requirements vs. Documentation

While "Documentation" often refers to manuals, in Software Engineering, the Requirements Model is the first and most critical documentation. It documents the intent of the software before code is written.

The Cost of Bad Documentation

If documentation is poor (tested in Ch 21), support costs rise. Users will call the help desk for simple tasks. Technical testing of docs ensures the instructions match the actual software behavior.

Answer 3: Reviews

Editorial Review: Finds grammar mistakes, confusing sentence structures, or poor formatting. Example: "The button click then." (Incomplete sentence).

Technical Review: Finds factual errors. Example: Manual says "Click Blue Button," but the software update changed the button to Red.
